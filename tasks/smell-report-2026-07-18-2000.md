# Architecture Smell Report

**Project:** TelOS (Life OS)
**Scope:** Full project (13 source files, ~4,700 LOC)
**Date:** 2026-07-18
**Analyzer:** smell skill (opencode)

---

## Executive Summary

TelOS is a vanilla-JavaScript single-page application for personal goal tracking and habit management. The codebase uses a **Big Ball of Mud** architecture with a loose tab-based feature separation. There is no module system, no framework, and no clear layering or separation of concerns. Everything is global — all functions, all state, all variables. While the code is functional and well-organized within each file, the architectural foundation is flat and unstructured.

The project has 3 **critical** issues (no tests, global state pollution, secret leakage risk), 7 **warnings** (god objects, anemic domain model, duplicated code, speculative generality, etc.), and several suggestions.

---

## Architectural Style Detected

**Big Ball of Mud** — No defined architecture. Files are grouped by feature (tabs) but there's no separation between data, business logic, and presentation layers.

### Style Expectations vs. Reality

| Expectation | Reality | Status |
|-------------|---------|--------|
| Clear module boundaries | All functions are global; no imports/exports; everything accessible everywhere | 🔴 |
| Separation of concerns | DOM manipulation, state mutation, and rendering mixed in same functions | 🔴 |
| Testable units | Zero test files exist | 🔴 |
| Consistent data access pattern | Plain object mutation throughout the codebase; no encapsulation | ⚠️ |
| Templating / component model | HTML strings built manually in JS functions; no component abstraction | ⚠️ |

## Detailed Findings

### Finding #1: No Tests

- **Category:** Testing
- **Severity:** 🔴 Critical
- **Anti-Pattern:** No Tests
- **Location:** Entire project
- **Description:** There are zero test files, no test framework in `package.json`, and no test scripts configured. All business logic (date calculations, streak computation, data validation) is untested.
- **Recommendation:** Add a test framework (Vitest or Jest) and unit-test pure functions in `utils.js`, `state.js`, and the data migration logic in `loadLocalData()`.

### Finding #2: Global State Pollution

- **Category:** Architecture
- **Severity:** 🔴 Critical
- **Anti-Pattern:** Big Ball of Mud / Static Cling
- **Location:** All `.js` files
- **Evidence:**
  - `appState`, `dbClient` in `state.js:8,26`
  - `activeTab`, `trackerDate`, `reviewTab`, `reviewMode`, `reviewWeekId`, `reviewMonth`, `reviewYear` in `app.js:10-15`
  - `careerEditMode` in `blueprint.js:8`
  - `constitutionEditMode` in `constitution.js:1`
  - `pendingCheckpointCompletion` in `execution.js:17`
  - `pendingNorthStarReviewCompletion` in `progress.js:254`
  - All functions are global (no modules, no IIFE, no ES modules)
- **Description:** Every function and state variable is globally accessible. There's no encapsulation, no module boundaries, and no dependency graph. Any function can mutate any state.
- **Recommendation:** Adopt ES modules (`type="module"` in script tags or a bundler). Encapsulate state behind accessor functions. Group related functions into modules with explicit exports.

### Finding #3: Secret Leakage Risk

- **Category:** Architecture
- **Severity:** 🔴 Critical
- **Anti-Pattern:** Technology-Enthusiast Architecture / Leaky Abstractions
- **Location:** `js/config.js:27-28`, `js/state.js:62-66`
- **Description:** Supabase credentials are stored in the config file and persisted to localStorage. These secrets are exposed in plaintext in the browser's dev tools and localStorage.
- **Recommendation:** Use environment variables or a backend proxy. At minimum, document that the anon key is meant to be public (Supabase anon keys are safe to expose, but educate users).

### Finding #4: God Files

- **Category:** Cohesion
- **Severity:** 🟡 Warning
- **Anti-Pattern:** God Object (file-level)
- **Location:**
  - `style.css` — 893 lines
  - `index.html` — 572 lines
  - `execution.js` — 499 lines
  - `progress.js` — 497 lines
  - `blueprint.js` — 427 lines
- **Evidence:** The three largest JS files each handle multiple concerns: rendering, event handling, data access, DOM manipulation, and state mutation.
- **Recommendation:** Split each tab file into smaller modules: e.g., `execution/render.js`, `execution/reflection.js`, `execution/deadlines.js`.

### Finding #5: Anemic Domain Model

- **Category:** Design
- **Severity:** 🟡 Warning
- **Anti-Pattern:** Anemic Domain Model / Data Class
- **Location:** `js/state.js:8-24`, `mockData.js:4-104`
- **Description:** The `appState` object is a plain data bag with no methods, no validation, no encapsulation. All logic operates on it externally. Adding a field requires changes in 5+ places (mockData, state, validation, render, etc.).
- **Recommendation:** Create typed data models with validation and serialization methods. Use factory functions for consistent object creation.

### Finding #6: Duplicated Code

- **Category:** Code
- **Severity:** 🟡 Warning
- **Anti-Pattern:** Duplicated Code
- **Location:** Multiple files
- **Evidence:**
  1. The levels array `[{ key: "sixMonth", label: "6-Month" }, ...]` is defined in `execution.js:329-333`, `progress.js:217-222`, `progress.js:234-239`, `execution.js:444`
  2. Magic string `"yea boi"` hardcoded in `execution.js:424` and `progress.js:298`
  3. ID generation pattern `"g_" + Date.now()` repeated in `blueprint.js:380` and similar patterns in `ai-goals.js`
- **Recommendation:** Extract the levels array to a shared constant. Define "yea boi" as a named constant. Create a utility function for ID generation.

### Finding #7: Speculative Generality

- **Category:** Design
- **Severity:** 🟡 Warning
- **Anti-Pattern:** Speculative Generality / YAGNI
- **Location:** `mockData.js:19`, `state.js:15`, `blueprint.js:381`
- **Evidence:** The `yearly` goals array exists in the data model but:
  - It's not rendered in the cascade UI (`cascadeLevels` skips it)
  - It's only used in `addNewGoal()` which can push to `yearly`, but no UI triggers this
  - It's included in `getDeadlinesForDate()` but has no visible effect
- **Recommendation:** Remove the `yearly` level unless there's a concrete plan to add it. It adds complexity and migration overhead for no benefit.

### Finding #8: Dead / Identity Functions

- **Category:** Code
- **Severity:** 🟡 Warning
- **Anti-Pattern:** Dead Code / Lazy Class (function-level)
- **Location:** `js/utils.js:158-159`
- **Evidence:**
  ```js
  function formatBlockActual(blockId, val) { return val; }
  function formatBlockTarget(blockId, target) { return target; }
  ```
  These functions return their input unchanged. They're called in `renderReviewMetrics()` but serve no purpose beyond indirection.
- **Recommendation:** Inline the calls or add actual formatting logic. If formatting isn't needed, remove the functions.

### Finding #9: Large Template Constant

- **Category:** Code
- **Severity:** 🟡 Warning
- **Anti-Pattern:** Long Method / Comments as Deodorant
- **Location:** `js/ai-goal-prompt.js:1-566`
- **Description:** A 566-line template string stored as a JS constant. This is more of a document than code. It inflates the JS bundle and makes the file hard to navigate.
- **Recommendation:** Move the prompt to a separate markdown or text file and load it at runtime. Or split it into sections that can be composed programmatically.

### Finding #10: Long Methods

- **Category:** Code
- **Severity:** 🟡 Warning
- **Anti-Pattern:** Long Method
- **Location:**
  - `progress.js:renderCascadeImpact()` — ~140 lines (lines 310-452)
  - `execution.js:renderAllGoalsCountdown()` — ~60 lines (lines 436-498)
  - `blueprint.js:renderLinkedHabitsList()` — ~90 lines (lines 233-323)
  - `blueprint.js:renderGoalsHub()` — ~55 lines (lines 24-79)
- **Description:** These functions handle rendering, data access, event binding, and DOM manipulation all at once.
- **Recommendation:** Extract rendering helpers. Separate HTML generation from data preparation.

### Finding #11: Render-Path Recompute

- **Category:** Complexity
- **Severity:** 🔵 Suggestion
- **Anti-Pattern:** Render-Path Recompute
- **Location:** `js/tabs/execution.js:renderToday()` → `renderHabitMonthGrids()`
- **Description:** Every call to `renderToday()` completely rebuilds the habit month grids, re-running all date calculations and DOM creation. There's no memoization or selective re-rendering.
- **Recommendation:** Since there's no virtual DOM, at minimum avoid re-rendering unchanged grids by comparing block data. Or implement a simple dirty-flag system.

### Finding #12: Nested Loops in Weekly Score

- **Category:** Complexity
- **Severity:** 🔵 Suggestion
- **Anti-Pattern:** Nested Loops
- **Location:** `js/utils.js:131-143`
- **Evidence:** `calculateWeeklyScore()` has nested `forEach` — iterating blocks and for each block iterating week dates.
- **Recommendation:** This is O(b × d) where b = blocks (max ~10) and d = days (max 7), so it's negligible. Flagged as suggestion only.

### Finding #13: Inconsistent Naming

- **Category:** Naming
- **Severity:** 🔵 Suggestion
- **Anti-Pattern:** Inconsistent Naming
- **Location:** Throughout
- **Evidence:**
  - Functions use `camelCase` (standard JS) ✓
  - Data fields use both `camelCase` (`biggestWin`, `northStarId`) and `snake_case` in some concept names
  - File naming has `ai-goals.js` (dash-separated) but `state.js`, `utils.js` (plain)
  - Variables like `nsId1`, `nsId2`, `g_s1` in mockData are not descriptive
- **Recommendation:** Adopt a consistent naming convention document and apply across the codebase.

## Dependency Graph Analysis

Since all functions are global and there are no imports/exports, every file depends on every other file implicitly. The dependency graph is a **complete graph** — 100% coupling. Files are loaded in a specific order in `index.html:559-570`:
```
mockData.js → config.js → state.js → utils.js → tab files → app.js
```

This ordering is critical but undocumented. Any reordering would break the app.

There are no circular dependencies (because there are no explicit imports), but the implicit coupling means every file depends on the global state and function namespace from all previously loaded files.

## Refactoring Roadmap

### Immediate Actions (This Sprint)
1. **Add tests** — Start with `utils.js` (pure functions, easy to test) and `state.js` (data migration logic)
2. **Extract shared constants** — Levels array, magic strings, ID utilities into a `constants.js` module
3. **Remove speculative `yearly`** — Clean up unused code paths

### Short-Term (1-3 Months)
1. **Adopt ES modules** — Convert to `type="module"` scripts with explicit imports/exports
2. **Encapsulate global state** — Replace raw `appState` access with getter/setter functions or a store pattern
3. **Split god files** — Break `execution.js`, `progress.js`, and `blueprint.js` into focused sub-modules
4. **Move AI prompt** — Extract `ai-goal-prompt.js` to an external text/markdown file

### Long-Term (3-12 Months)
1. **Component model** — Introduce a lightweight component/template system to replace manual HTML string building
2. **Data layer** — Create typed models with validation, serialization, and migration support
3. **Selective re-rendering** — Implement dirty-checking or a simple reactive pattern to avoid full re-renders
4. **CI/CD** — Add linting, type checking (JSDoc or TypeScript), and automated test runs
